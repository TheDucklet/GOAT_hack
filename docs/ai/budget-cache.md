# Дневной бюджет и кеш результатов

Два пакета ограничивают расходы на модели. `backend/app/ai/budget/` не пускает вызов к шлюзу, если дневной лимит команды исчерпан, `backend/app/ai/cache/` не вызывает модель повторно для входа, который уже обработан. Оба работают без сети, поэтому проверяются тестами с подставным провайдером (`backend/tests/test_ai_budget.py`, `backend/tests/test_ai_cache.py`).

## Дневной бюджет

Лимит команды 500 руб. в сутки хранится в `backend/app/ai/budget/limits.json`.

| Поле | Значение | Назначение |
| --- | --- | --- |
| `daily_limit_rub` | 500 | дневной лимит расходов |
| `utc_offset_hours` | 3 | часовой пояс МСК |
| `day_starts_at_hour` | 3 | час начала суток, совпадает со сбросом бюджета шлюза в 00:00 UTC |
| `chars_per_token` | 2.0 | пессимистичная оценка числа входных токенов по длине текста |
| `image_tokens` | 4000 | оценка входных токенов одного изображения |

Лимит можно заменить переменной `AI_LLM_DAILY_LIMIT_RUB`, а файл лимитов – переменной `AI_LLM_BUDGET_LIMITS_PATH`. Тарифы остаются в `backend/app/ai/providers/tariffs.json`.

### Порядок работы `call_llm`

1. Проверяются модель задачи и `max_tokens`, создаётся запрос.
2. Оценка стоимости считается по тарифам модели из длины входа и значения `max_tokens` как худшего случая вывода, затем резервируется в учёте (`BudgetLedger.reserve`). Если сумма потраченного, зарезервированного и новой оценки превышает лимит суток, вызов завершается ошибкой `budget_exhausted` без обращения к сети. Запись в журнале usage получает статус `budget_exhausted` и нулевую стоимость.
3. После ответа резерв заменяется фактической стоимостью из `usage.cost` шлюза (при её отсутствии – из токенов по тарифам). Неудачные вызовы без ответа возвращают резерв целиком, а ответ, который не разобрался как JSON, оплачивается, потому что шлюз его тарифицирует.
4. Если шлюз сам сообщил о превышении бюджета, сутки в локальном учёте закрываются, и следующие вызовы до сброса не доходят до сети.

Резервирование потокобезопасно, параллельные вызовы не могут вместе превысить лимит. Сутки считаются по МСК с началом в 3:00, то есть расход предыдущего дня не переносится на следующий.

### Журналы

- Журнал usage (`AI_LLM_USAGE_LOG_PATH`) хранит запись на каждый вызов: задача, модель, токены, задержка, статус, стоимость и источник стоимости.
- Журнал расходов (`AI_LLM_BUDGET_LEDGER_PATH`) хранит строку на каждое закрытие резерва (`request_id`, задача, модель, статус, зарезервированная и фактическая стоимость) и отметку о закрытии суток. При запуске процесс читает журнал и продолжает учёт, поэтому перезапуск сервера не обнуляет расход. Без пути учёт ведётся в памяти процесса.

Состояние суток показывает команда из каталога `backend`:

```bash
python -m app.ai.budget status --ledger storage/ai-budget.jsonl
```

### Ошибка для интерфейса

Исчерпанный лимит возвращается как `LLMError` с кодом `budget_exhausted` и текстом «Дневной лимит на обращения к модели исчерпан, дождитесь сброса в 3:00 МСК». Backend передаёт код и сообщение в задание, пользователь видит ошибку, а не пустой результат.

## Кеш результатов

`app.ai.bridge` отдаёт backend три функции с кешем: `summarize_event`, `derive_user_focus` и `build_insight`. Чат не кешируется, потому что зависит от истории диалога. OCR кешируется постранично на диске (`backend/storage/ai-cache/ocr`).

| Что кешируется | Части ключа |
| --- | --- |
| Суммаризация события | `event_id`, `event_version`, хеш всего входа, версия промпта, модели задач суммаризации |
| Фокус пользователя | хеш должности (без лишних пробелов) и интересов, версия промпта, модель |
| Карточка события | `company_id`, `profile_version`, `event_id`, `event_version`, `focus_hash`, `corpus_version`, версии промптов инсайта, агента и проверки оснований, модели всех задач агента |
| Страница OCR | хеш файла, номер страницы, версия промпта в имени файла, модель в записи |

Любое изменение любой части даёт новый ключ, а старая запись остаётся в хранилище, но не находится. Должность пользователя входит в карточку через `focus_hash`, профиль компании – через `profile_version`, источник – через `event_version` и `corpus_version`. Запись OCR другой модели не используется.

Хранилище выбирается переменными `AI_CACHE_DIR` (каталог с JSON-файлами, без него кеш лежит в памяти процесса и хранит до 512 записей) и `AI_CACHE_ENABLED`. Одинаковые запросы, пришедшие одновременно, вычисляются один раз. Ошибка вычисления в кеш не попадает. Из кеша возвращается копия, поэтому изменение результата вызывающим кодом не портит запись. Повторная карточка получает в трассе `cache: {hit: true, key}`.

### Версия корпуса

Ключ карточки требует `tools.corpus_version()`, то есть строку, меняющуюся при добавлении, замене или повторной индексации материалов банка. Если инструмент её не даёт, карточка строится без кеша, а счётчик пишет `insight.bypass`. Устаревшую карточку вернуть при этом нельзя, но и экономии нет.

## Проверки

| Сценарий | Тест |
| --- | --- |
| повтор одинакового запроса не увеличивает число вызовов модели (карточка, суммаризация, фокус) | `test_repeated_*` в `test_ai_cache.py` |
| смена должности, интересов, профиля, события, корпуса, промпта или модели даёт новый ключ | `test_changed_*` в `test_ai_cache.py` |
| резерв учитывает `max_tokens` и изображения | `test_reservation_estimate_counts_max_tokens_and_images` |
| исчерпанный лимит даёт ноль обращений к модели и явную ошибку | `test_exhausted_budget_*`, `test_limit_is_shared_*` |
| кеш не тратит бюджет даже при исчерпанном лимите | `test_cached_summary_costs_nothing_even_when_the_budget_is_exhausted` |
| сутки по МСК, перезапуск, параллельные вызовы | `test_budget_day_*`, `test_ledger_survives_restart_*`, `test_parallel_reservations_*` |

## Ограничения

- Учёт локальный. Если ключ используют несколько процессов или компьютеров команды, каждый видит только свои расходы, а общий остаток показывает `GET /key/info` шлюза. В этом случае закрытие суток по ответу шлюза защищает от перерасхода только после первой ошибки.
- Журнал расходов читается один раз при запуске, поэтому несколько процессов с одним файлом не видят расходов друг друга до перезапуска.
- Оценка входных токенов намеренно завышена (2 символа на токен), поэтому у границы лимита вызов с большим `max_tokens` может быть отклонён раньше, чем лимит исчерпан по факту.
- Стоимость вызова, повторённого после временного сбоя, учитывается один раз по последнему ответу.
