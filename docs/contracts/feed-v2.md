# Персональная лента v2

Задача A15 использует существующую очередь и общий контракт Insight v2.
Без параметров текущий frontend получает прежний FeedOut.
Для снимка передаётся contract_version со значением v2.

```http
GET /companies/{company_id}/feed?contract_version=v2&limit=20
GET /companies/{company_id}/feed?contract_version=v2&snapshot_id={snapshot_id}&limit=20&offset=20
```

Первый запрос создаёт или возвращает приватный снимок и одно задание feed_prepare.
GET читает данные и метаданные версий. Генератор и провайдер модели из GET не вызываются.
Повторные запросы с одинаковыми входами переиспользуют тот же снимок и задание.
Snapshot принадлежит конкретным user и company. Права проверяются при каждом чтении.

Изначально generation_status равен queued, items пуст и job_id доступен для обычного polling.
После завершения задания клиент перечитывает тот же snapshot_id.
Снимок становится ready после подготовки. У каждого элемента есть собственный generation_status.
В ready снимке могут остаться not_requested элементы за пределами оплачиваемого top K.
Только элемент ready содержит insight_id и персональный вывод сохранённой карточки v2.
Ошибки и нехватка бюджета дают failed или deferred. При смешанном результате снимок имеет статус partial.
Повтор GET не повторяет неуспешные обращения к модели.

Кандидаты отбираются детерминированно из не более 2000 последних видимых событий.
Дополнительно рассматриваются активные выводы из 200 последних сохранённых карточек пользователя.
Давняя дата источника сама по себе не исключает действующий долгосрочный вывод.
Сначала используются подтверждённые признаки и сохранённый фокус или явные интересы.
Worker уточняет фокус и порядок уже ограниченного списка кандидатов.
FEED_CANDIDATE_LIMIT по умолчанию равен 30 и ограничен 200.
FEED_PREPARE_TOP_K по умолчанию равен 3 и ограничен 10 и размером списка.
Генерация запускается только для активного профиля, обратившегося к ленте.
Обход всех сочетаний компаний и новостей отсутствует.

Ключ включает пользователя, компанию и версии profile, event, focus, corpus, prompt, model,
semantics, context_semantics, contract, schema, policy и generation.
Для app.ai.bridge метаданные моделей и промптов берутся из модулей Фёдора автоматически.
Для стороннего AI_MODULE владелец увеличивает AI_GENERATION_VERSION при изменении реализации.
Версия события учитывает исходную версию, заголовок, summary, topics, facts и дату.
Ключ снимка дополнительно включает день по Москве, набор кандидатов, лимиты, веса и политику ранга.
Точный повтор в течение дня не создаёт новую генерацию. Новый день допускает пересборку порядка
с повторным использованием карточек, чьи входные версии совпадают.

После завершения worker порядок и слоты снимка не меняются.
Пагинация использует фиксированные позиции. total обозначает количество сохранённых слотов.
Скрытые элементы отфильтровываются после выбора слотов страницы.
Поэтому страница может быть короче limit. Для продолжения используется next_offset.
Новые публикации читаются через новый запрос без snapshot_id.
Глобальное Event.visible и персональные feed_dismissals проверяются независимо.
Скрытие не сдвигает позиции и не дублирует элементы на следующей странице.
HTTP управление персональным скрытием дополняется в A16.

Политика feed-rank-2 добавляет к прежнему candidate_score фиксированные вклады.
Подтверждённые F14 уровни high, medium, low, undetermined дают 30, 20, 10, 0.
Актуальность active, review_required, undetermined, expired даёт 12, 3, 0, минус 40.
Без ссылок в соответствующем обосновании вклад равен нулю.
Числа из текста модели не извлекаются для ранга.
Прежняя свежесть источника даёт максимум один балл.
Каждая новая причина содержит factor, value, contribution, evidence_refs и policy.
Готовые карточки расположены перед неподготовленными. Внутри группы используются rank_score и event_id.
ranking_as_of и ranking_version показывают время и политику зафиксированного порядка.

При чтении перепроверяются версии и календарные сроки по Europe/Moscow.
После review_after выдаётся review_required. После окончания valid_until выдаётся expired.
Срок источника не превращается в срок действия вывода.
Возраст банковского документа рассчитывается отдельно по document_dates и действующей политике F14.
Длительный вывод без установленного конца не истекает через семь дней.
При изменении входов элемент становится stale и не выдаёт старый персональный вывод как готовый.
Чтение InsightOut также возвращает stale, stale_reasons и evaluated_at.
Сохранённая историческая запись остаётся в БД.

OpenAPI, feed-snapshot-v2.schema.json и feed-snapshot-v2-examples.json описывают тот же DTO.
Артефакты создаются scripts/export_feed_contracts.py.
Frontend получает FeedSnapshot и FeedSnapshotItem из сгенерированных типов OpenAPI.
