# Семантика клиентских данных v2 — A-14

Версия `company-data-2`, 22.10.2026. Первичный источник — `Кейс.pdf`, стр. 15–16,
и реальные заголовки трёх файлов `data1/`. Анализ вебинара — вторичный источник.
Решения и открытые вопросы: [questions.json](questions.json).
Результаты полного прогона: [a14-validation.json](a14-validation.json).

## Единый владелец и структура

`backend/app/data_semantics.py` задаёт версию, нормализацию и правила качества.
`services/client_import.py` отвечает за атомарный импорт и учёт исходных строк;
`services/client_context.py` — за CompanyContext v2, платежи и типизированные связи.
`services/clients.py` сохраняет прежние публичные точки входа без второй реализации.
Wire-модели находятся в `app/schemas.py`; AI, backend и frontend проверяют общие
`docs/contracts/company-context-v2-examples.json`. OpenAPI и TypeScript генерируются.

Модель признака:

```json
{
  "raw": ["1000"],
  "normalized": "1000",
  "value": null,
  "quality": "assumed",
  "issues": ["currency_unknown", "reporting_year_unknown", "possible_placeholder_1000_unconfirmed"],
  "unit": null,
  "period": "annual_year_unknown",
  "provenance": {
    "file": "df_Uid_data_hack.csv", "field": "REVENUE_COMPANY",
    "rows": [2], "file_sha256": "...", "semantics_version": "company-data-2"
  }
}
```

`raw` сохраняет написание значений всех строк; полные записи с исходными пробелами
хранятся в `client_raw_rows`. Для платежей полная исходная запись хранится в
`payments.raw`, рядом с batch_id и row_number. SHA256 фиксирует исходный файл.
`normalized` отражает преобразование записи, не подтверждает её бизнес-смысл.
`value` — совместимая проекция для существующих AI и ranking: непустая только
при quality=confirmed. `DataFeature` запрещает непустой value у сомнительного признака.
AI facts, каталог верификатора, ranking и сохранение evidence используют эту проекцию.
Отсутствующее значение не превращается в ноль или отсутствие продукта.

## Подтверждённое, предполагаемое и конфликтующее

| Данные | Статус смысла | Решение |
| --- | --- | --- |
| ORG_TYPE, OKFS_NAME, MAINOKVED_CODE/NAME, возраст, стадия бизнеса, градации работников | confirmed: определения на стр. 15 | Сохранять исходные градации как строки, не заменять точечным числом |
| CITY / REGION | confirmed | Регистрация юридического лица; не производство, обслуживание или место проживания физлица |
| CITY_NAME / RC_NAME | confirmed | Проживание связанного физлица, отдельные PersonLink; не копировать в географию компании |
| NEGATIVEMARK | confirmed | Бинарный признак ключевого собственника. Не кредитный риск; не определяет долю, конкретного человека или структуру владения |
| CL_PRODUCT_* / FACTORING_MARK | confirmed: наблюдаемый банковский флаг | 1/1.0/true → "1", 0/0.0/false → "0". Другие значения invalid, value=null. Флаг кредита не раскрывает сумму, ставку или все долги компании |
| CL_TYPE | confirmed как исходный код; нормализация по A-14 | CLIENT → Client; PROSPECT → Prospect; CLOSE_CLIENT → Closed Client. Все сохраняются. Неизвестный код → invalid, value=null |
| REVENUE_COMPANY | confirmed только как годовая выручка | Год, валюта и единица не подтверждены: normalized хранит число, quality=assumed, value=null |
| 1000 / 1000.0 в выручке | assumed | Возможная заглушка — гипотеза. Не объявлять нулём, подтверждённой выручкой или доказанной ошибкой источника |
| «Выручка 2025 в RUB» из вторичного анализа | assumed | Не записывать 2025/RUB без метаданных или подтверждения организатора; сейчас unit=null, period=annual_year_unknown |
| GROUP_ID | confirmed как совпадение кода группы | Не владение, не консолидация и не рыночная доля. Порог 15 млрд не применяется как подтверждённый факт |
| Общий SYNTHETIC_F | confirmed как связь через обезличенное физлицо | Отдельный shared_person; не назначать всем связанным лицам роль собственника |
| Платёж PAYER → BENEFICIARY | confirmed как наблюдаемая связь | Отдельный payment; не доказывает поставку, кредит или направление товарного потока |
| FTS_FLAG / FTS_COUNTRY_NAME | confirmed как запись / страна в ФТС | Направление импорта/экспорта, товары и объёмы неизвестны. Страна сама по себе не даёт признак импортёра или экспортёра |
| «Город обслуживания» из анализа | conflicting с первичным документом | Официальный смысл проживания физлица сохранён; альтернативная трактовка отмечена в журнале |
| Разные значения одного поля одного ID | conflicting | Сохранять raw всех строк; normalized/value=null, перечислить поле в unknowns |

Quality также включает missing, invalid, quarantined и legacy.
Пропуски `""`, nan, None, null регистронезависимы. Отрицательная/неконечная выручка
не публикуется как факт. Подтверждение валюты/года потребует новой версии политики,
повторной нормализации и соответствующих тестов; ручной SQL-патч value не заменяет её.

## Идентификаторы и дубли

Обычные повторы строк сохраняются целиком. Семантически одинаковые 1 и 1.0 не
считаются конфликтом. Конфликт только отрасли или GROUP_ID обнуляет это поле,
не удаляет остальные данные компании.

Версионированная эвристика подозрительного общего ID: известный технический
маркер (нулевой ID, unknown/common/undefined/-1/«общий») либо одновременные
разночтения **CITY и MAINOKVED_CODE** у одного SYNTHETIC_U. Это сигнал неоднозначной
идентичности для ручного разбора, не утверждение, что найдены разные юрлица.
Количество строк и конкретные значения ID в правило не входят.

Все строки такого ID остаются в raw с status=quarantine. Компания получает
identity_quality=ambiguous; её признаки имеют quality=quarantined и value=null,
GROUP_ID и client_type не становятся подтверждёнными. Связи физлиц с этим ID
помещаются в карантин; платежи сохраняются с classification=quarantined и
исключаются из внешних сумм и топ-контрагентов. Возможные ложные срабатывания
эвристики разбираются по исходным строкам и журналу; автоматического слияния нет.

## Платежи и учёт полноты

Фактический файл: **df_Uid_payment_hack.csv**, обязательные поля
BENEFICIARY/PAYER/PAY_AMT/PAY_CNT. Повтор названия файла физлиц на стр. 16 кейса
зафиксирован как опечатка: импорт не читает person-links как платежи.

Каждая корректная исходная строка остаётся отдельной записью Payment, включая
обычные дубли. PAY_AMT — Decimal с точностью источника до двух знаков; PAY_CNT —
положительное целое. Невалидная сумма/число, нарушенная структура CSV или изменение
файла во время чтения отменяют всю транзакцию, а не оставляют частичный snapshot.
Для PostgreSQL сохранён потоковый COPY; остальные вставки идут порциями.

Три непересекающихся класса платежей:

1. quarantined — хотя бы одна сторона неоднозначна/техническая;
2. self — PAYER=BENEFICIARY при однозначном ID;
3. external — остальные связи разных компаний.

Приоритет карантина выше self. Исходное число строк, сумма и количество платежей
равны сумме этих трёх классов. Суммы и количества сверяются раздельно.
`payment_summary` показывает внешние incoming/outgoing, self_payments,
quarantined и unclassified старых записей. Внешние top-10 не содержат self и
карантин. Unknown counterparty остаётся Company placeholder; у связи отмечен
counterparty_status=placeholder, профиль/отрасль/роль контрагента не выдумываются.

Период и валюта платежей не заданы подтверждёнными метаданными: period/unit=null.
Конец 31.10.2026 из анализа от 21.10.2026 не становится известной датой.
Объём платежей не называется выручкой или годовым оборотом.
Внутригрупповой платёж разных ID остаётся внешним для отдельного юрлица;
консолидированный оборот группы из этих сумм не строится.

## Связи и групповые суммы

`relationships` различает same_group/shared_person/payment, с происхождением
и направлением платежа. `related_companies` оставлен как совместимая проекция
групповых/персональных связей; платёжные соседи также доступны через payment_links.
Списки группы/физлиц ограничены 100 наблюдениями на тип, платежей — top-10 на
направление; relationship_coverage явно сообщает об усечении. Это не полнота рынка.

`group_summary` считает уникальные однозначные компании с общим GROUP_ID в
наблюдаемом наборе. Учитывает каждую компанию один раз. Для revenue_sum нужны
подтверждённые value/unit/period и совместимые единицы/периоды; число покрытых
компаний и общее число наблюдаемых членов выводятся рядом. При несовместимости
сумма=null. Сейчас валюта/год выручки не подтверждены, поэтому сумма не выдаётся.
Частичная сумма не объявляется полной: coverage_scope=observed_dataset,
is_consolidated=false. Рыночная доля не рассчитывается.

## CompanyContext, версии и доступы

CompanyContext v2 добавляет schema_version=v2, data_semantics_version,
identity_quality, client_type, payment_summary, relationships,
relationship_coverage и group_summary, сохраняя основные поля v1.
HTTP и AI inputs принимают v1/v2; backend возвращает v2. Исходные v1 fixtures
не изменены. Текущий генератор инсайта по-прежнему v1 и получает безопасные value;
генерация карточки v2 остаётся F-14.

profile_version — SHA256 от хешей трёх файлов **и версии семантики**. Тот же файл
после смены трактовки проходит повторный импорт. Обе ступени кеша включают общую
semantics policy и context_semantics; старый результат не переиспользуется как
новый. При прежнем файле и прежней семантике импорт идемпотентен.

CL_TYPE не создаёт Membership, не меняет user/system_role и не заменяет проверку
доступа. `demo-companies` выбирает только Client с однозначным профилем; Prospect
и Closed Client остаются в БД и доступны при явном действующем членстве.
`seed-demo` создаёт синтетические Client и переводит прежние demo-v1 на demo-v2,
сохраняя идентификаторы и членства. Синтетическое происхождение отмечено.

## Обновление существующей установки

Из backend, с настроенной DATABASE_URL и зависимостями requirements.lock:

```powershell
python -m app.cli migrate
python -m app.cli import-clients --directory ../../data1 --report ../artifacts/client-import-v2.json
python -m app.cli seed-demo
python -m app.cli demo-companies --limit 10
```

Для Compose: `docker compose up -d --build api worker`. Путь к CSV в контейнере
нужно передать через существующий volume или выполнить импорт из окружения с
доступом к тем же файлам; копии исходных CSV в образ не добавляются.
`seed-demo` требует прежнюю DEMO_PASSWORD и нужен для синтетического demo.

Миграция 0002 добавляет поля и raw-учёт; данные и членства сохраняются. Старым
профилям назначены legacy semantics/quality, платежам — classification=legacy.
Миграция не создаёт отсутствующие raw-строки задним числом. До повторного импорта
legacy-признаки не передаются AI как подтверждённые; unknowns содержит требование
повторного импорта. Исторические company/person raw и отчёты сохраняются по batch;
нормализованные платежи и их raw соответствуют активному snapshot, как и прежде.
Исторический отчёт не заменяет резервную копию исходного платёжного файла.

Полная воспроизводимая сверка предназначена для отдельной PostgreSQL **goat_a14**:

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
python scripts/verify_data_semantics.py --directory ../data1 --output artifacts/a14-validation.json
python scripts/export_data_contracts.py --check
```

Сверка проверяет каждую исходную/нормализованную платёжную строку, точные суммы
PostgreSQL NUMERIC, company/person raw, карантин, типы клиентов, отсутствие новых
Membership и идемпотентность. Скрипт откажется использовать другую БД. Промпты,
настоящие LLM и расходы для этой проверки не нужны.
