# Подготовка demo-доступов · R-07

Проводите подготовку до показа. Используются существующие регистрация, серверные сессии и членства A-02/A-03; изменения оператора записываются в AuditLog. Должность — свободный текст, она не меняет системную роль.

## Готовые учётные записи

Для отдельного локального demo-стека задайте `DEMO_PASSWORD` в игнорируемом корневом `.env`, запустите Compose по корневому README, затем выполните из корня репозитория:

```powershell
docker compose exec -T api python -m app.cli seed-demo
```

Seed создаёт две синтетические компании и готовые аккаунты. Пароль берётся из `DEMO_PASSWORD` контейнера. Повторный seed не меняет пароли уже существующих пользователей. Не выполняйте seed на БД с реальными клиентами ради демонстрации.

| Аккаунт | Системная роль | Начальный доступ | Подготовленный результат |
| --- | --- | --- | --- |
| admin@goat.example.org | admin | Членство не требуется для управления доступом | Оператор |
| user_a@goat.example.org | user | demo_company_a | Финансовый директор A; доступ к A и B |
| user_b@goat.example.org | user | demo_company_b | Генеральный директор A; второй ЛПР для A |

Один из двух ЛПР одновременно служит примером учётной записи с двумя компаниями. Компании «Демо компания A/B» имеют точные идентификаторы `demo_company_a` и `demo_company_b`. Для других импортированных компаний используйте существующие идентификаторы импорта; не подставляйте название вместо ID. В списке заявок A-03 возвращает company_id, поэтому UI явно показывает идентификатор компании.

## Подготовка двух ЛПР и доступа к двум компаниям

1. В отдельном окне войдите как user_a. В «Компании и профиль» задайте для A должность «Финансовый директор» и интересы. Подайте заявку на `demo_company_b` с той же или другой должностью.
2. В другом профиле браузера войдите как user_b. Подайте заявку на `demo_company_a`, укажите «Генеральный директор / международное развитие». Системная роль остаётся user.
3. В окне оператора войдите как admin и откройте `/admin/memberships` («Администрирование» → «Заявки и доступ»). Для каждой заявки сверяйте email, user_id, company_id и должность. Нажмите «Подтвердить доступ», проверьте данные в диалоге и подтвердите изменение.
4. Дождитесь «Доступ открыт» и сообщения об успехе. В окнах ЛПР нажмите «Обновить доступ» на странице компаний: она читает `/me`, затем обновляет список компаний. У user_a доступны A/B, у user_b появился доступ к A. В одной компании теперь два отдельных ЛПР со своими профилями и интересами.
5. До начала демонстрации проверьте вход и выбор компании у обоих ЛПР. Начинайте показ с готовых аккаунтов, а не с регистрации. Синтетическая подготовка не создаёт банковских заявок и не вызывает CRM.

Если нужна новая учётная запись, заранее зарегистрируйте её обычной формой `/register`, войдите и подайте заявку на компанию; затем подтвердите её оператором. Регистрация не создаёт admin и сама по себе не открывает компании. Первый настоящий администратор создаётся существующей CLI `python -m app.cli create-admin --email ...` с `ADMIN_PASSWORD` в окружении, как описано в backend README.

## Работа оператора

- `/admin/users`: email, ID, системная роль только для чтения, active/blocked. «Заблокировать»/«Разблокировать» требуют подтверждения. Блокировка отзывает все текущие сессии; разблокировка требует нового входа и не воскрешает старые сессии. Свой административный доступ отозвать нельзя.
- `/admin/memberships`: pending/active/rejected, пользователь, точные ID компании/членства, должность и интересы. «Отклонить заявку» не выдаёт доступ; «Отозвать доступ» переводит активное членство в rejected. Подтверждение членства заблокированного пользователя не разблокирует его аккаунт.
- `/admin/users/memberships` перенаправляет в тот же список заявок. `/admin` сохраняет сводку сервиса. Списки загружаются по 50 записей, «Загрузить ещё» продолжает выдачу; «Обновить список» перечитывает её с начала.
- Ошибка запроса не означает успех. Подтверждение остаётся открытым, статус не подменяется. «Повторить изменение» явно повторяет тот же PATCH статуса; автоматического повтора нет. При потере соединения запрос мог успеть выполниться на сервере — можно отменить диалог и перечитать список. При уходе со страницы ожидание отменяется, уже принятое сервером изменение этим не отменяется.
- Обычный пользователь получает 403 при прямом обращении к административным URL/API; отсутствие ссылки в навигации не заменяет серверную проверку. Подтверждённое членство открывает данные только после серверной проверки прав на каждом запросе.

## Существующие API и граница P2

Используются `GET /admin/users?limit&offset`, `GET /admin/memberships?limit&offset`, `PATCH /admin/users/{id} {status}` и `PATCH /admin/memberships/{id} {status}`. Cookie и CSRF передаются общим клиентом; пароли и токены не записываются в browser storage. Названия компаний не выдумываются из ID. Для подписей email список заявок один раз читает справочник пользователей страницами по 200 — существующий A-03 не возвращает email внутри MembershipOut. Для большого каталога дальнейшее улучшение — серверное включение метаданных и поиск, а не отдельный запрос на каждую строку.

Backend также поддерживает `PATCH /admin/users/{id} {system_role:"user"|"admin"}`. Эта операция изменяет системные права, записывается в аудит и отзывает сессии; собственное понижение запрещено. В интерфейсе R-07 редактора ролей нет. Расширенный редактор ролей, поиск/фильтры пользователей, массовые действия и отдельный onboarding остаются P2. Готовые операции PDF/новостей/заданий относятся к R-08, их интерфейс здесь не реализуется.

## Изолированная браузерная приёмка

Из корня репозитория; нужны Docker Compose с `!override` и Playwright 1.58.0/Edge:

```powershell
$env:IMAGE_TAG='r07-check'
docker compose -p goat-r07-check -f compose.yaml -f frontend/tests/compose.r07.yaml up --build -d --wait postgres api web
python frontend/tests/access_smoke.py --channel msedge --project goat-r07-check --output artifacts/r07-browser
docker compose -p goat-r07-check -f compose.yaml -f frontend/tests/compose.r07.yaml stop
Remove-Item Env:IMAGE_TAG
```

Используются только пустая БД `goat_r07`, localhost:8088 и проект `goat-r07-*`. Seed отказывается менять непустую БД. Пароль создаётся случайно и передаётся только через stdin в памяти процесса. Для повторного прогона возьмите новое имя проекта; прежние тома сохраняются. HTTP не перехватывается; PostgreSQL, сессии, CSRF, аудит и изменения прав настоящие. Worker и AI для этой проверки не нужны. [Отчёт R-07](../qa/r-07.md).
