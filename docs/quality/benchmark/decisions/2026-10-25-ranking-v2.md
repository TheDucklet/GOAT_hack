# F-16: решение до повторного замера

## 1. Протокол ranking и пороги

**Статус: APPROVED.** Утвердил Роман явным ответом «Утверждаю предложенный протокол» в этой рабочей сессии 25.10.2026; фиксация подтверждения: **01:45:02 МСК** (24.10.2026, 22:45:02 UTC). Текст подготовил Codex по запросу Романа. Новый платный benchmark этим решением не запускается.

Выбираем **B: nDCG@5 по меткам 0/1/2 и Recall@5 по метке 2**. Это внутренние цели команды, не норматив организаторов. Исходные run-1, targets.json, метки и FAIL сохраняются. Новый протокол — `ranking-v2`, новый run-id и отдельный файл targets; исторический отчёт не переписывается.

Вариант A при числе значимых событий M ≤ 5 даёт нормированную Precision = hits/M = Recall: он не добавляет независимой оценки. Вариант C требует менять плотность событий ради старого порога. Вариант B использует уже согласованную градуированную разметку и оценивает порядок выдачи.

Для контекста c: `DCG@5 = Σ (2^label_i − 1) / log2(i + 1)`, позиции i=1…5; gains для меток 0/1/2 равны 0/1/3. `IDCG@5` — идеальный порядок **того же** полного пула. `nDCG@5 = DCG@5 / IDCG@5`. Нет карточки, отказ или заблокированный результат не удаляет пару из пула; событие не входит в пользовательский top-5, незаполненная позиция имеет gain=0. Отказ не может улучшить результат за счёт уменьшения знаменателя.

| Gate новой выборки | Порог, все условия обязательны |
| --- | --- |
| nDCG@5 macro | ≥ 0,80 |
| nDCG@5 pooled | ≥ 0,80; `Σ DCG / Σ IDCG`, это явно определённая агрегированная версия, а не стандартное среднее nDCG |
| Recall@5 micro | ≥ 0,70; `Σ hits(label=2) / Σ M` |
| Recall@5 macro | ≥ 0,70; среднее по контекстам с M>0 |
| Сравнение с event-ranker | Разности nDCG macro/pooled и Recall micro/macro ≥ 0 на одном пуле и одних метках |
| Устойчивость относительно baseline | nDCG не хуже baseline минимум в 80% оцениваемых контекстов; при семи — минимум 6/7, равенство считается «не хуже» |
| Достаточность оценки | nDCG определён для всех 7 контекстов; Recall — минимум для 5/7; иначе оценка INCOMPLETE, release-gate не пройден |

При IDCG=0 nDCG=N/A, при M=0 Recall=N/A; такие контексты не превращаются в 0 или 1 и не исчезают из отчёта. Публикуются число оцениваемых/N/A и причины. Для каждого контекста сохраняются DCG, IDCG, hits, M, top-5 и число выданных результатов. Для всех агрегатов — числители/знаменатели либо сумма и число слагаемых.

Обычные Precision@5 и Recall@5 сохраняются в отчёте: micro и macro, знаменатель Precision=5 на контекст, включая пустые позиции; потолок `min(5,M)/5` на контекст и его агрегаты. Precision не заменяется молча Recall. В новом протоколе у обычной Precision нет отдельного порога 0,60; решение действует только для нового замера. При M>5 потолок и знаменатель считаются по полной разметке, а не найденным карточкам.

Порядок при равных оценках фиксируется до замера: исходный score по убыванию, затем event_id по возрастанию. Оба ranker получают одинаковые версии контекстов, события, as_of и размеры candidate pool/top-5; baseline не получает преимущества от другого набора. Итоги отдельно на исходных 84 парах и на новом отложенном наборе, без смешивания. Gate ranking должен пройти на **отложенном** наборе; старые регрессионные метрики публикуются отдельно.

Все прежние независимые ограничения сохраняются: 0 критических неподтверждённых фактов, 0 ложных позиций банка, 0 межкомпанейских утечек, GCR ≥ 0,90 после ручной калибровки и независимого контроля судьи; доля содержательных различий ролей ≥ 0,50. Критическое нарушение блокирует приёмку даже при высоких средних. Успешный ranking не закрывает публикационный gate, R-10 или R-11.

## 2. Положительные случаи и покрытие

Общий критерий успешного положительного случая: финальный программный допуск `allow`, сохранённая ready-карточка, содержательный персональный механизм, точные ссылки на проверенный факт события **и** подтверждённый признак компании, согласованные выводы и действия. Одного наличия текста/claim_id недостаточно: содержание оценивается по источникам. `bank_view=null` допустим с честной причиной; пустой анализ, boilerplate или служебный отказ успешной карточкой не считаются.

**Не требуем заранее определённого ненулевого impact по одному продуктовому флагу.** Уровень low/medium/high допускается только по опубликованным критериям и доступным основаниям. Если для силы влияния не хватает данных, `undetermined` с конкретными неизвестными допустим и не отменяет полезный условный механизм. Для B06 `undetermined` обязателен. Это уточняет предложенный шаблон и сохраняет требование не выдумывать экспозицию.

Шесть случаев 1–6 должны пройти **6/6**; случай 7 также обязателен как отдельная регрессия. Каждый проверяется после публикационного gate через действующий worker/API, а не только по объекту до финальной сборки v2. Известный банкинг-дефект может привести к удалению bank_view; оставшийся анализ заново проверяется.

Для всех исходных 84 пар и всех новых 42 пар **раздельно**: ready coverage ≥90% (`успешные содержательные ready / все запрошенные пары`). Явные окончательные отказы по качеству допускаются максимум для 10%: не более 8/84 и 4/42. Неизвестность сама по себе не повод блокировать честный условный анализ. `undetermined` и отсутствие bank_view не равны отказу, но не дают автоматический PASS содержательности.

Транспортные/программные ошибки после разрешённых ограниченных повторов — отдельный технический gate: **0 окончательно потерянных пар**; они также остаются в знаменателе coverage. Публикуются первые неудачи, все повторы, время и стоимость; бесконечная перегенерация до удачного примера запрещена. Допускается не более одной исправляющей попытки содержания согласно remediation; при исчерпании — финальный отказ, без маскировки ready.

Для GCR отдельно публикуются все существенные утверждения, неизвестные/неоценённые вердикты, покрытие проверки и результаты по разделам. Удалённые утверждения и отказы не скрываются. Если нет обязательной ручной калибровки/контроля судьи, итог INCOMPLETE независимо от автоматической оценки.

## 3. Новые события, отложенный набор и фиксация

**Шесть новых событий, все шесть — отложенный контрольный набор.** До замера на них запрещены правки промптов, валидатора, scoring и критериев под результат. Для разработки и калибровки остаются исходные 12 событий, известные дефекты и их отдельные перефразировки. Такой порядок не делит шесть событий на пул из трёх: top-5 по трём кандидатам сделал бы Recall тривиальным. Ограниченность контроля из шести событий явно указывается; это не статистическое доказательство качества на всех новостях.

Состав фиксируется до получения ответов моделей:

| Категория | Число | Правило |
| --- | --- | --- |
| Регуляторные / макроэкономические | 2 | Публичные материалы Банка России, разные события; URL, время публикации, сохранённый полный текст и SHA-256. Не пересказы и не копии события о ставке из run-1. |
| Отраслевые | 2 | По одному для разных отраслей профилей; допускается маркированная синтетика с вымышленными числами. Без добавленных специально под компанию свойств. |
| Нейтральные или косвенные | 2 | Заранее выбранные события без доказанной прямой экспозиции контекстов; минимум одно реальное публичное сообщение Банка России. Не объявлять их автоматически меткой 0: метку дают люди. |

Итого минимум **3 реальных события**, синтетика явно помечена в данных и отчёте; исходный текст источника и синтетический сценарий не смешиваются. Шесть событий должны отсутствовать в run-1, F-17 и материалах настройки; повтор URL, того же события или близкий пересказ не является новизной. Временные ограничения не позволяют использовать опубликованное после as_of.

Для отбора реальных событий заранее закрепляются окно публикаций, перечень источников, критерии включения/исключения и правило порядка, например хронологический порядок с URL для разрешения равенств. Для синтетики — seed и сценарии. Если подходящих событий нет, фиксируется недостаточность пула; нельзя добирать удобные примеры после просмотра генерации или меток.

Каждое событие оценивается на **всех семи контекстах** из run-1: B01/chief_accountant, B01/procurement_director, B02–B06/finance_director. Это **42 пары**; B01 и B02 дают сопоставление продуктовых отметок 1/0 в одной отрасли, два ЛПР B01 — различия ролей без изменения прав. B06 сохраняет неполный профиль. Роль — сохранённый пользовательский фокус, не способ расширить доступ.

Роман и Алексей независимо размечают все 42 пары по исходным событиям, корректно нормализованным профилям и роли **до просмотра результатов ranker и карточек**. Шкала: 0 — персональная значимость не обоснована; 1 — косвенная/условная; 2 — существенный обоснованный повод для решения/проверки в данной роли. Метка 2 не означает, что неизвестная экспозиция стала фактом. Автоматизация допустима для подготовки форм, но не для выдачи подписи/метки за человека.

Сохраняются обе исходные метки, основания, разногласия и согласованная метка. Неразрешённые пары не удаляются: разметка INCOMPLETE. Разметка значимости отдельно от проверки утверждений и калибровки judge. Контроль judge из remediation (не менее 30 независимых утверждений) не заменяется этими 42 метками значимости.

До платного прогона фиксируются в репозитории: утверждённый decision record с временем МСК, отдельные targets `ranking-v2`, полные входы и их хеши, роли/контексты, as_of, метки и способ согласования, правила ранжирования, версии генератора/валидатора/судьи, SHA кода. После этого — новый run-id, общий бюджетный ledger, лимит расходов, concurrency и retries. **Разрешение на живую приёмку R-10 до 5 ₽ не является разрешением на новый benchmark F-16.** Бюджет F-16 согласуется отдельно до его запуска.

Нельзя выбирать лучший повтор или менять targets/метки после результата. При FAIL сохраняются входы, ошибки и отрицательный итог; после исправления нужен новый run-id. Использованный для исправлений контрольный набор становится регрессионным, следующий контроль собирается заново до следующего замера.
