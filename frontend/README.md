# Frontend · R-01 / R-03 / R-04 / R-05 / R-06 / R-07 / R-08

Общий Docker-запуск web/api/worker/postgres теперь описан в [корневом README](../README.md). Docker-сборка frontend всегда использует HTTP API через nginx; инструкция ниже предназначена для отдельной разработки frontend.

React + TypeScript + React Router; сборка Vite. Node.js 24.22.0 (минимум 24.15 в ветке 24), npm. Зависимости зафиксированы в package-lock.json.

Из корня репозитория:

```powershell
cd frontend
npm ci
Copy-Item .env.example .env
npm run dev
```

Открыть <http://127.0.0.1:5173>. Файл-пример явно включает локальный mock. Без `.env` используется настоящий HTTP API, автоматического переключения на mock при ошибке нет.

Демонстрационный вход: `demo@example.org` или `admin@example.org`; пароль `Demo-password-2026`. Это синтетические аккаунты только mock-адаптера. Пользователь начинает без сессии. Для проверки 503 используйте email `unavailable@example.org`, для 403 — `blocked@example.org`, для 422 отправьте пустую форму регистрации. Непустой пароль позволяет дойти до сценариев 403/503 на форме входа. Прямой `/admin` под `demo@example.org` также возвращает 403.

Маршруты: `/login`, `/register`, `/app`, `/app/companies`, `/app/analytics`, `/admin`, `/admin/users`, `/admin/memberships`. Авторизация восстанавливается через `/me`; защищённый URL после входа сохраняется. Общий header содержит компанию и имя из локальной части email, поскольку отдельное поле имени в User отсутствует. Страница аналитики содержит ленту R-04, карточку R-05 и контекстный чат R-06; R-07 добавляет управление пользователями и заявками с подтверждением действий.

На `/app/companies` показаны все собственные членства: active, pending и rejected. Имена активных компаний приходят из `/companies`; для остальных показан идентификатор. Заявка требует идентификатор, полученный у администратора: публичного каталога компаний в API нет. Должность — произвольный текст до 1000 символов, интересы — до 30 строк; проверяет сервер. Кнопка «Обновить доступ» перечитывает `/me`, после подтверждения компания становится доступной в header. Должность не меняет системную роль. Профиль можно заполнить и до подтверждения заявки.

В dev-mock новая регистрация и изменения членств сохраняются только в памяти адаптера; перезагрузка страницы или перезапуск dev-сервера сбрасывают эти данные. Реальные перезагрузки страницы и сохранение профиля проверяются на HTTP API, как описано ниже.

## Настоящий backend

В `.env` установить:

```dotenv
VITE_API_MODE=http
VITE_API_BASE_URL=/api
API_PROXY_TARGET=http://127.0.0.1:8000
```

Vite проксирует `/api/*` в backend без префикса `/api`; браузер работает с одним origin. Для отдельного API можно указать полный `VITE_API_BASE_URL`, например `http://127.0.0.1:8000`; backend должен разрешать конкретный frontend origin и credentials в CORS. Согласовать cookie/SameSite/HTTPS с Алексеем. Секреты и LLM-ключи не помещать в VITE-переменные: они видны браузеру.

Один HTTP-клиент `src/shared/api/index.ts` используется feature API в `src/features/*/api.ts`. Cookie отправляются через `credentials: include`; `X-CSRF-Token` берётся из `/me` или login и хранится в памяти. CSRF добавляется к изменяющим защищённым запросам. Auth-данные не записываются в localStorage/sessionStorage. В mock используется отдельная JS-cookie с синтетической идентичностью; она не является настоящей защищённой сессией. Сессию HTTP-режима создаёт только backend.

Композиция маршрутов — `src/app`, поведение — `src/features`, общие UI/transport/types — `src/shared`. Layout не владеет загрузкой компаний: её выполняет CompanyProvider. Поля и ошибки форм используют FormField/ErrorNotice. [Полная структура и добавление будущих задач](../docs/architecture.md). `npm run architecture:check` проверяет границы и циклы; `npm run architecture:test` проверяет сам guard на контрольных нарушениях. Оба шага выполняются в CI.

## Проверки и сборка

```powershell
npm run contracts:check
npm test
$env:VITE_API_MODE='http'
npm run build
npm run preview
```

Mock запрещён в production-сборке. Для локальной демонстрации используйте dev-сервер. `npm test` проверяет маршруты, формы, роли, обработку ошибок, cookies и CSRF без backend и LLM-ключей. Build проверяет TypeScript и создаёт `dist/`; preview слушает <http://127.0.0.1:4173>.

На production-хостинге необходим SPA fallback: `/login`, `/register`, `/app`, `/app/companies`, `/app/analytics`, `/admin` должны отдавать `index.html`. Пример для nginx:

```nginx
location /api/ {
    proxy_pass http://api:8000/;
}
location / {
    try_files $uri $uri/ /index.html;
}
```

Vite dev/preview уже поддерживают прямые URL. Docker и общая конфигурация nginx/CI — задача R-02.

Типы генерируются из опубликованной A-01 (7f86298), примеры импортируются прямо из `docs/contracts/examples.json`. При изменении OpenAPI выполнить `npm run contracts:generate`, затем `npm run contracts:check` и тесты. HTTP-примеры и дополнительные обёртки mock проверяются по JSON Schema 2020-12. Внутренний AI-пример UserFocus отсутствует в HTTP OpenAPI и проверяется тестами A-01 на стороне Python.

Для повторения браузерного прогона, оставив dev-сервер с mock включённым:

```powershell
python -m pip install playwright==1.58.0
python tests/browser_smoke.py --channel msedge
```

Если Edge отсутствует, установить Chromium: `python -m playwright install chromium` и запустить без `--channel`. Скрипт проверяет прямые URL, 401/403/422/503, вход/выход и ширину 390px; сохраняет отчёт и снимки в `docs/qa/`.

После HTTP-сборки и запуска preview можно отдельно проверить настоящий fetch и cookie/CSRF на перехваченных ответах A-01: `python tests/http_smoke.py --channel msedge`. Это проверка транспорта браузера, не интеграционная проверка живого backend.

Контракт экранов и точные форматы запросов описаны в [ui-requests.md](../docs/contracts/ui-requests.md). Подключён живой backend A-13, включая auth и членства A-02/A-03.

Приёмка R-03 на работающем Docker-стеке после `seed-demo`, из корня репозитория:

```powershell
python frontend/tests/membership_smoke.py --channel msedge
```

Требуется тот же Playwright 1.58.0. Скрипт создаёт одного нового синтетического пользователя и его членство; seed-администратор меняет только это новое членство. Существующие пользователи и членства не изменяются. По умолчанию используется локальный адрес 127.0.0.1:8080 и `demo_company_a`; параметры `--base-url`, `--company-id`, `--output` позволяют их изменить. Для своего seed задайте `R03_ADMIN_EMAIL` и `R03_ADMIN_PASSWORD` в окружении, не в командной строке. Отчёт и три скриншота сохраняются в `artifacts/r03/`; пароли, cookie и CSRF в отчёт не попадают. Скрипт использует настоящий HTTP и не перехватывает ответы. [Результаты R-03](../docs/qa/r-03.md).

## Персональная лента R-13 поверх R-04

С главной страницы откройте «Бизнес-аналитика». Лента читает `GET /companies/{id}/feed?contract_version=v2`: основной текст — сохранённый персональный вывод и механизм, рядом показаны сила/основание влияния, горизонт, актуальность и неизвестные. Новость остаётся отдельным основанием. Источники раскрываются по клику через авторизованный API. Статусы ожидания/отказа/неопределённости не заменяются готовым анализом.

Ожидание snapshot опрашивает тот же id раз в 2 секунды, не более 120 секунд. Следующие страницы закреплены за этим id, в том числе при скрытии всех слотов страницы. Готовность перепроверяется раз в 45 секунд и при возврате в окно; stale скрывает прежний preview. «Обновить ленту» запрашивает актуальный снимок. Деталь читает сохранённый insight_id; запросов генерации на render и N отдельных запросов за карточками нет. Компания/пользователь изолированы общим AnalyticsSelection; восстановленный чат сохраняется.

Браузерная приёмка R-13 использует новый отдельный Compose-проект с пустой БД, двумя синтетическими профилями и настоящим worker. AI явно синтетический, серверный ключ пустой. Не запускайте seed-demo вручную: скрипт создаёт собственные фикстуры. Из корня репозитория:

```powershell
$env:IMAGE_TAG='r13-check'
$env:AI_ENV_FILE='.env.ai.example'
docker compose -p goat-r13-check -f compose.yaml -f frontend/tests/compose.r13.yaml up --build -d --wait
python frontend/tests/prepared_feed_smoke.py --project goat-r13-check --channel msedge
docker compose -p goat-r13-check -f compose.yaml -f frontend/tests/compose.r13.yaml stop
```

Для повтора используйте новое имя `goat-r13-*`; порт 8094 должен быть свободен. Скрипт не перехватывает HTTP, не отправляет документы/CSV в модели; пароль остаётся в памяти. Результаты — `artifacts/r13/browser/`; [приёмка R-13](../docs/qa/r-13.md). Прежние `feed_smoke.py`/`feed_fixture.py` и [отчёт R-04](../docs/qa/r-04.md) сохранены как историческая проверка ленты v1; для текущего UI используйте R-13.

## Карточка R-05

Выберите событие и нажмите «Подготовить анализ». Карточка читает buildInsight/insight/jobs через существующий HTTP-клиент. Готовый ответ 200 показывается сразу; задание 202 опрашивается раз в две секунды. Повтор чтения после сетевой ошибки сохраняет принятый job. «Проверить актуальность» читает серверный stale; «Обновить анализ» вручную запрашивает новую версию. Смена компании или события отменяет запросы и ожидание.

Отдельно показаны факты, банковский материал, гипотезы/сценарии ИИ, риски, возможности, действия и неизвестное. V2 добавляет механизм влияния, его силу и основание, горизонт, предпосылки и сроки актуальности. В v1 отсутствующие оценки не подставляются. Notice_v1 всегда находится внутри панели. Кнопка «Основание N» открывает авторизованную новость, точное поле профиля или PDF с датой и страницей. Чтение готового insight_id предусмотрено для будущей ленты R-13 без дополнительной генерации.

Изолированная браузерная приёмка R-05, из корня репозитория:

```powershell
$env:IMAGE_TAG='r05-acceptance'
docker compose -p goat-r05-check -f compose.yaml -f frontend/tests/compose.r05.yaml up --build -d --wait
python frontend/tests/insight_smoke.py --channel msedge --project goat-r05-check
docker compose -p goat-r05-check -f compose.yaml -f frontend/tests/compose.r05.yaml stop
Remove-Item Env:IMAGE_TAG
```

Скрипт требует Playwright, свободный порт 8086 и пустую изолированную БД goat_r05. Для повторения используйте новое имя проекта goat-r05-*. Пароль генерируется в памяти и не входит в отчёт. Проверяются настоящие HTTP/cookie/CSRF, PostgreSQL, worker и защищённый PDF; перехвата HTTP нет. Только тестовый Compose override включает `tests.fake_feed_ai` и учебные сохранённые карточки, отключает внешний шлюз и сбор новостей. Такой прогон подтверждает интерфейс и интеграцию, а не качество или стоимость реальной модели. Обычный Compose использует серверную конфигурацию AI из корневого README. Отчёт и снимки: `artifacts/r05/`; [приёмка R-05](../docs/qa/r-05.md).

## Чат R-06

В «Бизнес-аналитике» выберите событие, введите вопрос и нажмите «Отправить вопрос». Уточняющие кнопки заполняют поле, отправка остаётся явной. Ответ появляется после фонового задания; источники, ограничения и предупреждение находятся внутри диалога. URL с `chat_id` восстанавливает компанию, событие и всю серверную историю после reload.

При сетевой ошибке, отказе бюджета и повторном входе вопрос сохраняется для ручного повтора. Уже принятый вопрос не дублируется. Несохранённый черновик хранится в памяти вкладки и теряется при полном reload; принятая сервером история остаётся в БД. Смена компании очищает прежний диалог и прекращает ожидание. [Контракт и состояния](../docs/contracts/ui-requests.md#контекстный-чат-r-06).

Изолированная браузерная приёмка, из корня репозитория (Docker Compose с поддержкой `!override`, Playwright 1.58.0 и Edge):

```powershell
$env:IMAGE_TAG='r06-check'
docker compose -p goat-r06-check -f compose.yaml -f frontend/tests/compose.r05.yaml -f frontend/tests/compose.r06.yaml up --build -d --wait
python frontend/tests/chat_smoke.py --channel msedge --project goat-r06-check --output artifacts/r06-browser
docker compose -p goat-r06-check -f compose.yaml -f frontend/tests/compose.r05.yaml -f frontend/tests/compose.r06.yaml stop
Remove-Item Env:IMAGE_TAG
```

Порт — 8087, БД — только `goat_r06`. Для повторного прогона используйте новое имя проекта `goat-r06-*`: seed отказывается менять непустую БД. Тома сохраняются после остановки. Фикстуры R-05 переиспользуются; дополнительный `chat_fixture_ai` явно синтетический, без gateway/платных вызовов. HTTP, PostgreSQL, очередь, worker и сохранение истории настоящие, перехвата запросов нет. Бюджетный отказ, остановка API и истечение сессии проверяются на собственных тестовых данных. [Отчёт и снимки](../docs/qa/r-06.md).
